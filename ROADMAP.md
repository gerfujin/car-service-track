**Цель v1.0:** опубликованный продукт: личный кабинет + лендинг + единый дизайн + интеграции.

## Правила работы

1. **Один этап за раз.** Этап закрыт, только когда отмечены все его DoD-чекбоксы.
2. **main всегда зелёный.** Работа в коротких ветках, мерж только с зелёным билдом и тестами.
3. **`git tag` перед крупными переделками** и при закрытии каждого этапа — точки отката (ты это уже практикуешь).
4. **Тесты пишутся вместе с фичей**, а не «потом».
5. **Новые идеи → сразу в Backlog** (внизу файла), а не в текущий этап. Scope creep — убийца №1 pet-проектов.
6. **Ритм важнее марафонов:** 2–3 коротких сессии в неделю лучше одного воскресного рывка. Заканчивай каждую сессию заметкой «следующий шаг: …» — так резко проще начать следующую.
7. **SaaS-швы (задел под v2.0, действует на всех этапах).** В v1.0 остаёмся single-tenant, но новый код пишем так, чтобы multi-tenancy потом не потребовала переворачивать проект:
   - **Не хардкодить «workshop всегда один».** Любые данные сервиса (название, услуги, контакты) читаются из БД по id workshop'а — никаких `.First()` «потому что он один», никаких констант и синглтонов в конфиге.
   - **Сущности связаны с `Workshop` там, где это естественно** (услуги, механики, заказы). `WorkshopId` на сущности — это будущий `TenantId`; глобальный query-фильтр EF Core потом ляжет на него одной строкой.
   - **Изоляция модулей — свято** (её и так охраняет арх-тест из 1.2). При переходе на tenant'ы фильтрация добавляется в каждый модуль независимо, не распутывая клубок перекрёстных ссылок.
   - **Один claim-путь для identity.** Как с `AppUserId`: когда появится `tenant_id` в JWT, читать его должен один helper — второй путь чтения claims = будущий тихий баг.

**Легенда оценок:** S ≈ 1 вечер · M ≈ 2–4 вечера · L ≈ 5+ вечеров. Оценки грубые — для порядка, не для дедлайнов.

### 🏢 v2.0 — SaaS (multi-tenancy): главный кандидат на «большую» вторую версию

Превращение продукта «под один автосервис» в платформу, к которой подключаются много сервисов. Открывать **только после `v1.0`** и целиком, как самостоятельный этап со своими DoD. Что входит:

- **Tenant-модель:** `WorkshopId` → `TenantId`; глобальные query-фильтры EF Core (`HasQueryFilter`) добавляют `WHERE TenantId = @current` ко всем запросам — тот же паттерн, что IDOR-фильтр по `AppUserId`, уровнем выше
- **Tenant resolution middleware:** субдомен/slug (`autofix.carservicetrack.com`) → текущий tenant в контексте запроса; claim `tenant_id` в JWT (читается одним helper'ом, см. правило 7)
- **Роли:** нынешний `admin` становится админом своего сервиса; новая роль `super-admin` платформы (подключение сервисов, подписки)
- **Onboarding:** регистрация нового автосервиса = создание tenant + первого админа
- **Два вида лендинга:** продуктовый лендинг платформы (продаёт софт владельцам сервисов) + страница каждого tenant'а (шаблон = лендинг этапа 2, данные из его записи в БД)
- **Биллинг:** подписки через Stripe (Checkout + webhooks из 4.2 — уже готовый фундамент)
- **Seed и тесты** переводятся на 2+ tenant'а: главный тест изоляции — клиент сервиса А не видит ни одной сущности сервиса Б

**Почему не сейчас:** это ещё ~один «этап 4» по объёму, а полузаконченный SaaS хуже законченного v1.0. Всё, что делается в этапах 1–5, переиспользуется в v2.0 — при соблюдении правила 7 переход будет добавлением слоя, а не переворотом проекта.
